### PDF preview hardened against open-Word + flaky COM (this session, user report)
- **Reported symptom:** DOCX generated fine, but the viewer said "PDF preview is currently unavailable on this server."
- **Root cause found:** the app's `WINWORD.EXE` PID 228 was the user's own interactive Word, open at 9:24 AM on **the SF-001 template**. Word is single-instance per user session, so every automation launch attached to that window, set `$word.Visible = $false` (hiding the user's document), and **called `$word.Quit()`** on the way out — i.e. the converter could steal/close the user's Word, hang on a busy instance (→ 422), and previously left leaked windowless `WINWORD` processes behind after force-kills, contaminating later COM attaches.
- **Fixed engine (`src/lib/documents/pdf.ts`):**
  - **Ownership via `Visible`:** if COM returns the user's visible Word we attach safely — never hide it, never Quit it. A fresh hidden launch is treated as owned, hidden, and Quit after export.
  - **State file** (`start → created-owned/created-attached → opening → exporting → exported`): success is decided by `exported` + a non-empty PDF, so cleanup noise (the PS `finally` under `$ErrorActionPreference='Stop'`) can never mask a completed export — this was turning real successes into 422s.
  - **Pre-run orphan sweep:** windowless WINWORD instances in the same session are force-reaped so COM never attaches to a half-dead server; a post-failure sweep + one retry handles transient stalls. The user's windowed document is never matched (main-window check).
  - **422 `hint` enum** (`word_busy` / `word_unavailable` / `conversion_failed`) surfaced to the client; `PdfPreview` now shows specific guidance and a **Retry preview** button in the fallback; route logs include `reason=…`.
